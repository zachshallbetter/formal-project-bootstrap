# Governance

Formal Project Bootstrap is intentionally conservative. The repository should grow by evidence, not by accumulation.

## Change classes

**Editorial correction** restores an existing rule and may be a patch.

**Repository capability** adds tooling, checks, examples, or optional profiles without changing the core contract.

**Normative change** changes authority, work authorization, evidence semantics, autonomy boundaries, context rules, or other operating invariants. It requires a dedicated protocol-change issue and explicit compatibility assessment.

## Anti-bloat test

Before adding a canonical concept, determine whether the need can be represented by reference, binding, specialization, constraint, projection, qualification, or composition. If so, use that mechanism instead.

## Evidence requirement

A change should state the problem it closes and the evidence that the problem exists. New abstractions without an observed failure mode remain proposals.

## Human authority

Repository maintainers retain release and normative-change authority. Automation may prepare, verify, and recommend; it does not manufacture approval.
